# THIS FILE MADE A PREDICTION BEFORE COMMIT 5b AND THE PREDICTION WAS WRONG.
#
# It was captured immediately before the mailbox-state work and it took two
# obligations: `bare` MUST NOT MOVE, and the four mailbox worlds MUST MOVE and
# move apart from each other. It argued at length that a commit satisfying only
# the first "would be a commit that did nothing at all, and this file would have
# applauded it."

# Commit 5b then shipped -- binding_run51, conditions 1-8, PASS_REF_AND_NATIVE,
# including ic_ref == ic32 == golden on a route-bearing, mailbox-bearing,
# overflow-bearing three-epoch fold. All five rows below are still identical.
# The second obligation was not merely unmet; it was aimed at the wrong surface.
#
# WHY IT WAS THE WRONG SURFACE. These three columns measure WORLD state. A
# mailbox is CLAIM state. The two are different spaces and 5b put the mailbox in
# the second one, which is what binding_run49 R12 had already measured and what
# binding_run51 now pins from both ends:
#
#   T1   with no mailbox, MAP emits the frozen 2-field EpochControl.
#   T1b  WITH one it emits PAIR(EpochControl, bundle) -- the EpochControl STILL
#        has exactly two fields. What grew is the REDUCER's output, not the
#        WORLD's input, so `compile_step_v6` steps the same state it always did.
#   T8b  the reduced world state carries no mailbox at all; every mailbox line
#        in a film matched against golden was REBUILT from the emitted bundle.
#
# A world-state fingerprint cannot see a claim-state feature. The old note
# reasoned correctly that a mailbox must have runtime state somewhere and then
# assumed "somewhere" was `_v6_fields`, because that is the state these columns
# happen to hash. The assumption was never measured. It should have been.
#
# TWO THINGS THIS FILE PREVIOUSLY ASSERTED, BOTH RETRACTED:
#
#   * "binding_run43 10.16 asserts the opposite and 5b MUST AMEND IT", with a
#     three-way split proposed (object_order survives, epin-/obsv- survive,
#     slay-/blay- INVERT). 10.16 says "D8: the mailbox moves NO backend
#     fingerprint". It is green today, after 5b, and it is CORRECT. Nothing
#     inverts and nothing needs splitting. Leave the row alone.
#
#   * "the ruling's obligation (3), 'route-free v1 terms byte-identical', cannot
#     mean what it says, and the frozen class is the MAILBOX-free class."
#     Obligation (3) means exactly what it says and is satisfied literally.
#     `profile_for_artifact` selects on ROUTES: a mailbox-DECLARING but
#     route-free world stays on admit.ic.v1.core52 and its terms are byte-
#     identical (run51 T2, 13 emitters, no drift; T2c; run50 S9d). The
#     observation underneath the retracted claim is still true and still
#     relevant -- `init_claimstate` and the Film v0.7 projection both fork on
#     DECLARATION, so a route-free mailbox world does carry claim state and does
#     emit mailbox film lines. That is simply not a statement about v1 terms.
#
